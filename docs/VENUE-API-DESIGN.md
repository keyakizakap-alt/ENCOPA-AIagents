# 実店舗API接続 メモ（2026-09-21 更新）

ホットペッパーグルメAPIによる実店舗検索は **`app/api/venues/route.ts` に実装済み**（`main` の "Add real restaurant search" / "Add nationwide prefecture venue search"）。本書は当初の設計案を、実装済みの現状に合わせて整理したものである。

## 1. レイヤーの整理（変更なし）

**空席照会と予約実行を提供する汎用APIは存在しない。** 店舗情報の検索APIと予約台帳のAPIは別レイヤーで、後者は事業者契約が前提である。

| レイヤー | 現状 |
|---|---|
| 店舗検索（都道府県・予算・人数・個室） | **実装済み**（ホットペッパー グルメサーチAPI） |
| 店舗詳細（住所・アクセス・営業時間・URL・写真） | **実装済み** |
| リアルタイム空席照会 | 未実装（一般提供なし） |
| 予約の実行 | 未実装（同上） |

UIが表示している「空席未確認」「このアプリから予約は実行しません」という但し書きは、引き続き**事実として正しい**。

## 2. API選定の記録

| API | 採否 | 理由 |
|---|---|---|
| **ホットペッパー グルメサーチAPI** | **採用** | 予算・人数・個室という本アプリの検索軸を条件として直接持つ。無料 |
| Google Places API (New) | 不採用 | 宴会向けの予算帯・個室条件を持たない。Text Search は Pro $32/1,000件で主経路には高い |
| ぐるなび レストラン検索API | 不採用 | 無料提供は2021年6月終了、現在は法人向け有料のみ |
| 食べログ | 不採用 | 一般向けAPIなし |

## 3. ⚠ 未解決：利用規約の確認

**実装は済んでいるが、規約の確認は完了していない。** 以下は公開運用の前提を覆しうる。

1. **ホットペッパーAPIの商用利用可否** — 「商用利用はできない」とする解説記事が複数存在する（**非公式**）。公式利用規約は本環境の egress ポリシーにより直接確認できておらず、**未検証**。公開サービスとして運用するなら最優先で確定させること
2. **レート制限** — 1日あたりの上限が公式に明記されているか未確認。現在の防御は `limit('venue-search:<ip>', 30, 3600)` のみで、サイト全体の日次上限は無い
3. **画像・データの取り扱い** — 店舗写真（`imgfp.hotp.jp`）の表示条件と帰属表示の要否

商用利用が不可と判明した場合の代替は、(a) ぐるなび法人向け有料APIの契約、(b) Google Places 単独＋予算・個室条件の自前推定、(c) 幹事が店舗情報を手入力する既存のグループ機能を正式仕様とする。(c) は既に完成しており、コストもリスクも最も低い。

## 4. 残っている技術的な改善余地

- **`/api/venues` にキャッシュが無い** — 同一都道府県・条件の検索が毎回プロバイダへ到達する。店舗情報は分単位で変わらないため、`encopa_agent_cache` と同じ仕組み（条件を帯に丸めたキー＋共有テーブル、TTL 6〜24時間）を入れる価値が大きい。レート制限にも効く
- **サイト全体の日次上限が無い** — クライアント単位（30件/時）のみ。`ENCOPA_AGENT_DAILY_LIMIT` と同様の全体上限を検討
- **再試行・サーキットブレーカが無い** — `/api/agent` には実装済みだが `/api/venues` には無い。8秒タイムアウトで失敗すると即エラー
- **障害時に古い結果を出す経路が無い** — 失敗時は候補ゼロ。`stale-while-error`（期限切れキャッシュを「最終更新: ◯時間前」と明示して表示）が使えると体験が安定する
