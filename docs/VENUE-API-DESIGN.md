# 実店舗API接続 設計方針（2026-09-21 調査）

現在の候補カード6件（`app/page.tsx` の `venuePool`）は比較ロジック確認用の**架空店舗**であり、実店舗検索・空席照会・予約実行はいずれも未接続。本書はそれを実データへ置き換えるための設計である。

調査日: 2026-09-21 / 本環境は egress ポリシーにより一部の公式ドキュメントへ到達できず、**未検証**と明記した項目がある。着手前に該当箇所の公式確認を必須とする。

---

## 1. 最初に確定すべき前提

**空席照会と予約実行を提供する汎用APIは存在しない。** 今回調べた範囲では、店舗情報の検索APIと、予約台帳（予約実行）のAPIは別レイヤーであり、後者は事業者契約が前提である。したがって段階を分けて考える必要がある。

| レイヤー | 実現可否 | 手段 |
|---|---|---|
| 店舗検索（エリア・予算・人数・ジャンル） | **可能** | 下記の検索API |
| 店舗詳細（住所・電話・営業時間・URL） | **可能** | 同上 |
| リアルタイム空席照会 | **不可**（一般提供なし） | 予約台帳事業者との個別契約が必要 |
| 予約の実行 | **不可**（同上） | 同上 |

現在のUIは既に「空席未確認（デモ）」「このアプリから予約は実行しません」と表示しており、**この前提自体は正しい**。実店舗に接続しても、当面この但し書きは維持される。

## 2. 検索APIの比較

| API | 提供状況 | 費用 | 日本の飲食店網羅性 | 出典 |
|---|---|---|---|---|
| **ホットペッパーグルメ グルメサーチAPI** | 提供中 | 無料 | 高（予算・人数・個室などの条件検索が可能） | [リクルートWEBサービス](https://webservice.recruit.co.jp/doc/hotpepper/reference.html)（公式） |
| **Google Places API (New)** | 提供中 | Pro $32/1,000件、無料枠 月5,000件 | 高（ただし宴会向けの予算・個室条件は無い） | [Places API 利用と課金](https://developers.google.com/maps/documentation/places/web-service/usage-and-billing)（公式） |
| **ぐるなび レストラン検索API** | **無料提供は終了** | 法人向け有料のみ | 高 | [ぐるなびマーケティングソリューション](https://solution.gnavi.co.jp/service/gnavi_api/)（公式） |
| 食べログ | 一般向けAPIなし | — | — | — |

**ぐるなびAPI**は新規登録を2021年1月15日に停止、無料提供を2021年6月30日で終了し、現在は法人向け有料サービスへ移行している（非公式まとめによる記述。契約検討時は公式へ直接確認すること）。

### 推奨：ホットペッパーグルメAPIを第一候補、Google Placesを補完

理由は**条件の一致**である。本アプリの検索軸は「目的・エリア・予算・人数・個室・食事制限」であり、ホットペッパーのグルメサーチAPIはこのうち予算・人数・個室を検索条件として直接持つ。Google Placesはテキスト検索と評価・写真に強い一方、**宴会向けの予算帯や個室条件を持たない**ため、`rankVenues()` が必要とする入力を満たせない。

Google Placesは「ホットペッパーに載っていない店舗の住所・地図補完」として併用するのが費用対効果が良い。Text Searchは1,000件あたり$32（Proティア）で、評価やレビューを含めるとEnterpriseティア（$35〜$40）へ繰り上がるため、**検索の主経路に据えるとコストが跳ねる**。

### ⚠ 着手前に必ず確認すること（未検証）

1. **ホットペッパーAPIの商用利用可否** — 「商用利用はできない」とする解説記事が複数存在するが、**公式利用規約で確認できていない**（本環境から `webservice.recruit.co.jp` へ到達不可）。本アプリを公開サービスとして運用するなら、これは設計の前提を覆しうる最重要事項である。規約本文と、必要ならリクルートへの問い合わせで確定させること。
2. **ホットペッパーAPIのレート制限** — 1日あたりの上限が公式に明記されているか未確認。
3. **Google Maps Platform のキャッシュ制限** — Google の規約は取得コンテンツの保存期間を制限し（place ID を除き一時的な保存のみ）、表示時の帰属表示を要求する。後述のキャッシュ設計はこの制約に従う必要がある。**規約本文の確認が必須。**

## 3. アーキテクチャ設計

既存資産をそのまま再利用できる。`/api/agent` で作った**キャッシュ・上限・再試行・ブレーカ・フォールバック**の構造は、そのまま店舗検索にも当てはまる。

```
クライアント
  └─ POST /api/venues  （新規／同一Origin・JSON・16KiB上限は既存の readBody をそのまま使用）
       ├─ 1. 共有キャッシュ参照（encopa_venue_cache）
       ├─ 2. クライアント単位・サイト全体の上限（既存 limit()）
       ├─ 3. 外部API呼び出し（再試行＋サーキットブレーカ、既存パターン）
       └─ 4. 正規化して返却
クライアント
  └─ rankVenues() でローカル決定的スコアリング（★変更しない）
```

### 3.1 順位付けは引き続きローカル

外部APIは**候補集合を供給するだけ**で、順位は `rankVenues()` が決める。これは今回の決定（「AIは説明文のみ、順位は決定的」）と同じ思想であり、外部データの揺れで順位が不安定になることを防ぐ。`VenueBase` 型はそのまま使い、APIレスポンスをこの型へ正規化する層を1つ挟む。

`base` / `conversation` / `access` / `value` といったスコア原資は架空店舗用の手入力値なので、実データからの導出規則を決める必要がある（例：`value` = 予算帯と実価格の乖離、`access` = 駅からの距離）。**導出できない指標は、スコアから外すか一律値にする。実データに無い数字を捏造しない。**

### 3.2 キャッシュ設計（コストの要）

店舗情報は分単位で変わらないため、キャッシュの効きが非常に大きい。

| 項目 | 設計 |
|---|---|
| 表 | `encopa_venue_cache`（`encopa_ai_cache` と同形式） |
| キー | `SHA-256(プロバイダ:APIバージョン:エリア:予算帯:人数帯:条件)` |
| 人数・予算 | **帯に丸める**（例：人数を5名刻み、予算を500円刻み）。18名と19名で別クエリを投げない |
| TTL | ホットペッパー：6〜24時間。Google Places：**規約上の保存期限に従う**（要確認、place ID 以外は短期） |
| 清掃 | 既存と同じく書き込みの一部で期限切れ行を削除＋`pnpm db:cleanup` |

帯への丸めが最も効く。エリアの選択肢が有限（駅名）であることを考えると、実質的なキー空間は小さく、**ヒット率は高くなる見込み**（未実測）。

### 3.3 障害時の挙動（fail-closed を維持）

外部APIが落ちたとき、**架空のデモ店舗を代わりに出してはならない。** 実在すると誤認させる方が、候補が出ないことより有害である。

1. 共有キャッシュに期限切れの行があれば、「最終更新: ◯時間前」と明示して表示（stale-while-error）
2. それも無ければ、候補ゼロで「店舗情報を取得できませんでした」と表示し、手入力でのグループ作成へ誘導
3. デモ店舗は**開発環境専用**にフラグで隔離する

### 3.4 セキュリティ

- 新しいAPIキーは `/api/venues` のサーバ側のみで使用し、クライアントへ出さない（`NEXT_PUBLIC_` を付けない）
- 外部APIのレスポンス（店名・住所・説明文）は**外部入力**として扱う。Reactは文字列としてエスケープするが、`website` などURL項目は既存 `reservation()` と同じく `https:`/`http:` のみ許可する
- 店舗名・説明文を将来LLMへ渡す場合は、`/api/agent` と同じく「データであって指示ではない」扱いを徹底する

## 4. 段階的な進め方

| 段階 | 内容 | 判断材料 |
|---|---|---|
| 0 | **規約確認**（商用利用可否・キャッシュ制限・レート制限） | ここで可否が決まる。先に実装しない |
| 1 | `/api/venues` を追加し、ホットペッパーAPIから検索。`rankVenues()` はそのまま | 正規化層と `VenueBase` の埋め方が焦点 |
| 2 | 共有キャッシュと上限を接続し、実測でヒット率とコストを確認 | 帯の刻み幅を実測で調整 |
| 3 | デモ店舗を開発専用へ隔離し、本番は実データのみ | 障害時の表示を先に用意してから切り替える |
| 4 | Google Places を住所・地図の補完として併用（必要なら） | Pro SKU 無料枠 月5,000件の範囲で足りるか |
| 5 | 予約台帳連携（TableCheck / トレタ等）の可否調査 | 事業者契約が前提。**別案件** |

段階0で商用利用が不可と判明した場合の代替案は、(a) ぐるなび法人向け有料APIの契約、(b) Google Places 単独＋予算・個室条件を自前で推定、(c) 幹事が店舗情報を手入力する現在の方式を正式な仕様とする、の3つ。(c) は既にグループ機能として完成しており、**実は最もコストもリスクも低い**。
