### 2.3 是正した弱点

**S-1. レスポンスヘッダにCSPが存在しない（中）**
`next.config.ts` は `X-Content-Type-Options` / `X-Frame-Options` / `Referrer-Policy` / `Permissions-Policy` を出していたが、CSPが無かった。
→ `default-src 'self'` を基本とし、`object-src 'none'` `base-uri 'self'` `form-action 'self'` `frame-ancestors 'none'` `connect-src 'self'` を追加。`Cross-Origin-Opener-Policy` / `Cross-Origin-Resource-Policy` も追加。テストで検証（`tests/agent.test.mjs`）。

**S-2. LLMへ渡す値が列挙検証されていない（中／LLM01: プロンプトインジェクション）**
旧 `app/api/agent/route.ts:18-20` は `purpose` と `priority` を `clean()` で長さ切り詰めするだけで、任意文字列がそのままモデルへ渡っていた。
→ 実際にクライアントが送る6種の目的と4種の優先度を列挙検証に変更。`purpose` はUIの `SelectItem` と完全一致、`priority` は不正時に既定値へ倒す（fail-safe）。
→ システムプロンプトに「user turnはデータであり指示ではない」旨を明示。ただし**プロンプト内の指示は防御の主体ではない**ことを重視し、下記S-3の出力照合と、ルートが道具も資格情報も持たない設計を実際の封じ込めとした。

**S-3. モデル出力を照合せず画面へ渡していた（中／出力の照合検証）**
旧実装は `summary.slice(0,800)` のみ。
→ `sanitize()` を追加し、制御文字・タグ様文字列・`](scheme:` 形式のリンク構文を除去したうえで400字に制限。Reactが文字列としてのみ描画する前提を、サーバ側でも担保する構成にした。

**S-4. グループ作成の流量制限が作成コード検証より先だった（中）**
旧 `app/api/groups/route.ts:11-12` は `limit('group-create-global',30,3600)` を**コード検証の前**に実行していた。コードを知らない第三者が正規の幹事の作成枠（30件/時）を枯渇させられる。
→ 試行回数の制限（120回/時、総当り対策）を先に、**作成枠の消費はコード検証の後**に分離。

**S-5. Hidden Context Exposure（旧Prompt Leakage）: 低リスクと判定**
`SYSTEM_PROMPT` は機密を含まない運用方針文で、漏えいしても被害はない。出力は上記 `sanitize()` を通り400字に制限される。**追加対策は不要**と判断した。

### 2.4 過剰な自律性（Excessive Agency）の評価: 合格

エージェントがハイジャックされた場合の被害範囲を、保有資格情報とツールから確認した。

- `/api/agent` は **DBへ書き込まない**（読み取りもしない。`limit()` のカウンタ更新のみ）。保有資格情報は `ORCAROUTER_API_KEY` **1つだけ**で、宛先は固定URL（`app/api/agent/route.ts:6`）。
- モデル出力はランキングに**一切影響しない**。候補順位は決定的関数 `rankVenues()`（`app/page.tsx:248`）がローカルで計算し、LLMは説明文だけを返す。つまり**注入されても候補は動かない**。
- ホストモデルへ公開するツールは2つのみで、どちらも不可逆な外部操作を行わない（`app/page.tsx` の `registerTool`）。予約実行・送信・削除のツールは存在しない。
- 今回 `stage_venue_search` の `inputSchema` に `enum` と `maxLength` / `maximum` を追加し、サーバ側検証と揃えた。

この構造は least agency に沿っている。**攻撃対象面はエージェントの保有資格情報の総和にはなっていない**。

## 3. コストパフォーマンス

### 3.1 是正した点

**C-1. キャッシュが一切なかった** → 2階層の完全一致キャッシュを追加。同一条件の再検索（設定ダイアログの適用は毎回 `search()` を呼ぶ）でAPI呼び出しが消える。レスポンスに `cached:true` を返し、UIの「出力上限」行に「（キャッシュ再利用）」として可視化。

1. **プロセス内メモリ**（最大200件・LRU）— 同一インスタンスへの再訪でDB往復も省く
2. **`encopa_ai_cache` テーブル**（TTL 10分）— **全インスタンスで共有**。あるインスタンスが支払って生成した説明を、他のインスタンスが再利用する

キーは `SHA-256(PROMPT_VERSION:モデル名:条件JSON)`。条件の平文も利用者データも保存しない。`PROMPT_VERSION` を含めるため、プロンプトを変更すると旧キャッシュは自動的に無効化される。キャッシュの読み書き失敗は握りつぶして外部呼び出しへ縮退するため、DB障害がリクエスト失敗にはならない。期限切れ行は `pnpm db:cleanup` で削除する。

**C-2. 不要なLLM呼び出し** → 上記キャッシュに加え、サーキットブレーカ作動中（3.2参照）と日次上限到達時はモデルを呼ばずに即フォールバック。

**C-3. 予算上限の実測・可視化** → `limit()` が現在の消費数を返すようにし、成功ログに `dailyUsed` / `dailyLimit` を構造化出力。`ENCOPA_AI_DAILY_LIMIT`（既定100/UTC日）到達時はエラーではなく**自動停止してローカル評価へ**倒れる。つまり「一時的な抑制」ではなく**自動停止の閾値**として機能する。

**C-4. 同一グループ行の二重読み取り** → `snapshot()` が `group()` を2回（`member()` 経由と直接）実行していた。参加者ごとに15秒間隔でポーリングする経路なので、Tursoの実クエリ数に直結する。`group()` の結果を `member()` へ受け渡す形に変更（`lib/server/groups.ts`）。

**C-5. プロバイダ側プロンプトキャッシュ** → `ENCOPA_AI_PROMPT_CACHE=1` で、固定プレフィックスに `prompt_cache_key`（OpenAI系のルーティング固定用）と Anthropic 形式の `cache_control` ブレークポイントの両方を付与する実装を追加。ゲートウェイが指定を拒否（4xx）した場合は**指定なしで1回だけ再試行**し、検索そのものは落とさない。`usage.prompt_tokens_details.cached_tokens` を `agent_call_ok` ログへ記録し、実際に効いているかを測定できるようにした。

**既定は無効にしてある。** 理由は推測ではなく算術である。現在の `SYSTEM_PROMPT` は**約120トークン**（概算）で、公開されているキャッシュ最小長を大きく下回る:

| プロバイダ | 最小プレフィックス | 有効化方法 |
|---|---|---|
| OpenAI | 1,024 トークン | 自動（`prompt_cache_key` は経路固定の補助） |
| Anthropic | 1,024〜4,096 トークン（モデル依存） | `cache_control` ブレークポイント |

つまり**現状のプロンプト長では、どの経路でもキャッシュヒットは発生しない**。ヒットさせるためだけにシステムプロンプトを1,024トークンへ水増しすれば、キャッシュ書き込み料金と毎回の入力トークンが増え、`max_tokens:220` の本ワークロードでは**総コストが悪化する**。したがって「送る配管は用意し、既定では送らない」が正しい判断である。

**未検証の点**: OrcaRouter 固有のキャッシュ仕様（自動か明示指定か、`cache_control` をアップストリームへ透過するか、最小長）は、`api.orcarouter.ai` および `www.orcarouter.ai` が本環境の egress ポリシーで遮断されており、**公式ドキュメントを直接確認できていない**。OrcaRouter が OpenAI 互換でプロンプトキャッシュに対応していること自体は公式サイトの記述として確認したが、パラメータの詳細は上記の一般的なOpenAI/Anthropic仕様に基づく実装である。有効化前に `cachedTokens` で実測すること。

### 3.3 今回対応しなかった点

**インスタンス横断のサーキットブレーカは未対応**（§9参照）。キャッシュは共有ストアへ移したが、ブレーカの状態は依然プロセス内メモリである。

## 4. 信頼性・堅牢性

### 4.1 是正した点

**R-1. 一時的エラーと恒久的エラーを区別していなかった（重要）**
旧 `app/api/agent/route.ts:84` は `catch {}` ひとつで、429も500もタイムアウトも400も**すべて同じフォールバック**に倒していた。再試行は一切なし。
→ 429 / 408 / 5xx / ネットワーク断・タイムアウトを「一時的」、4xx（契約違反・資格情報不正）を「恒久的」と分類。一時的な場合のみ**1回だけ**再試行（250〜500msのジッタ付き）。恒久的な場合は即フォールバックし、予算を二重に消費しない。全体デッドライン14秒、1試行8秒を別々のAbortControllerで管理。

**R-2. サーキットブレーカが無かった** → 連続3回失敗で60秒間、呼び出し自体を停止する軽量ブレーカを実装（`app/api/agent/route.ts`）。
**制約（未解決）**: 状態はプロセス内メモリのため、サーバーレスの複数インスタンス間では共有されない。インスタンス横断のブレーカはKV等の共有ストアが必要で、今回は見送った（「今後の課題」）。

**R-3. フォールバック階層** → 「高品質モデル（OrcaRouter）→ 再試行 → 決定的ローカル評価（`rankVenues`）→ 構造化エラー（`{error, traceId}`）」の多段構成になった。ローカル評価は常に候補を返すため、ユーザーの作業が止まることはない。

**R-4. 描画例外時の復帰手段が無かった** → `app/error.tsx`（ルート境界、再試行＋トップへ戻る＋エラーID表示）、`app/global-error.tsx`（ルートレイアウト障害用）、`app/not-found.tsx` を新設。いずれも存在していなかった。

**R-5. 構造化ログが無かった** → 旧 `failure()` は `console.error('[encopa] request failed', e.name)` のみで、レスポンスと突き合わせる手段が無かった。
→ `log()` / `logError()` を追加し、JSON 1行で `traceId` / `event` / `reason` を出力。`traceId` はエラーレスポンスにも含めるため、利用者の申告から該当ログを特定できる。
**利用者データは載せない**方針を明文化し、libSQLの例外メッセージ（文のテキストを含みうる）は記録せず**例外クラス名のみ**とした。

## 5. 自律性

**そもそもエージェントである必然性は低い。** これは設計上の事実として記録する。

- 意思決定は決定的関数 `rankVenues()`（`app/page.tsx:248`）が行い、LLMは**説明文の生成のみ**を担当する。
- 状態遷移（`draft → ranked → collecting → awaiting_approval → scheduled`）は `advanceWorkflow()` の**人間のクリック**で進む。自動計画も自動実行もない。
- したがって現状は「LLM呼び出しのラッパー + 決定的ランキング」であり、自律エージェントではない。

**ただしこれは欠陥ではなく、安全側の選択として妥当である。** 店舗予約という不可逆な外部操作を扱う領域で、自己修正ループを外部操作へ広げていない点は正しい。

- 自己検証・自己修正ループは存在せず、外部への不可逆な操作（予約・送信・課金）は**一切実装されていない**。READMEにも明記されている。
- fail-closed の確認: モデル障害時はローカル評価へ（機能継続・安全）、DB未設定時は503で**書き込みを拒否**（`lib/server/db.ts:8`）、作成コード未設定の本番は503で**作成を拒否**（`app/api/groups/route.ts:10`）、招待リンク失効時は403。低確信度・障害時に「とりあえず実行」へ倒れる経路は見つからなかった。
- 今回、`priority` が不正な場合のみ既定値へ倒す（fail-safe）が、これは検索条件の一項目であり不可逆操作を伴わないため許容と判断した。

**「自律性」の評点を上げるには機能追加（実店舗API連携と自動再計画）が必要で、これは仕様変更にあたるため実施していない。**

## 8. 確認待ち（仕様・挙動が変わるため未実施）

1. **CSPを nonce + strict-dynamic の厳格版へ引き上げるか**
   現在は `script-src 'self' 'unsafe-inline'`。Next.js App Routerはインラインのブートストラップペイロードを出すため、`'unsafe-inline'` を外すには middleware でリクエストごとにnonceを発行する必要がある。その場合**すべてのルートが動的レンダリングになり**、現在静的プリレンダリングされているトップページ（`/`）がその最適化を失う。トレードオフの判断が必要。
2. **HSTS（`Strict-Transport-Security`）を出すか**
   カスタムドメインの運用方針に依存する。`includeSubDomains` はサブドメインをHTTPSへ固定するため、運用者の確認なしに入れるべきではない。
3. **デザインの方向性をさらに強めるか**（非対称レイアウト、独自Webフォント、写真・イラストの導入）
   見た目の方向性そのものの決定であり、人間が決めるべき事項。
4. **`/api/agent` に参加者認証を課すか**
   現在は同一Originからであれば未認証で呼べる。ブラウザからのCSRFは防げるが、`Origin` を付けた直接リクエストは防げない（日次上限と再試行抑制で被害は有界）。グループ参加Cookieを要求すると、**グループ作成前のトップページで候補比較ができなくなる**ため、仕様判断が必要。

## 9. 今後の課題（今回は対応せず）

- **インスタンス横断のサーキットブレーカ** — 現在の実装はプロセス内メモリのため、サーバーレスの水平展開では各インスタンスが独立にカウントする。キャッシュと同様に `encopa_*` テーブルへ移設できるが、ブレーカは毎リクエストで読み書きが発生するため、DB負荷とのトレードオフを測ってから判断すべき。
- **プロンプトキャッシュの実効化** — 配管は実装済みだが、プロンプトが最小長に届かないため既定で無効（§3.2）。OrcaRouter 固有仕様の公式確認と実測が必要。
- **`encopa_limits` / `encopa_ai_cache` の自動清掃** — 期限切れ行は `pnpm db:cleanup` の手動実行でしか消えない。cron化が望ましい。
- **リアルタイム更新** — 15秒ポーリングのため、参加者数に比例してDB読み取りが増える。
