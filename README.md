# ENCOPA（エンコパ）

**飲み会の幹事がやっている作業を、ひとつの流れにまとめるアプリです。**

| | |
|---|---|
| 動かすもの | 全国47都道府県の**実在する店舗**（ホットペッパーグルメWebサービス） |
| 使っているAI | OrcaRouter経由の多段エージェント（統括→専門担当→再統合） |
| 技術構成 | Next.js 16 / React 19 / TypeScript / Tailwind CSS v4 / Turso (libSQL) / Vercel |

---

## 1. 課題

忘年会の幹事を引き受けると、作業はこう散らばります。

> グルメサイトで店を探す → 条件に合うか一軒ずつ見比べる → チャットに候補を貼る → 出欠を集計表に書き写す → アレルギーの有無を個別に聞いて回る → 決まった内容をもう一度チャットに貼る → カレンダーに入れる

**店探し以外のすべてが手作業で、情報はサイト・チャット・表計算・カレンダーの4か所に散らばります。**

そして最大の問題は、**一度決めた条件を変えると最初からやり直しになる**ことです。「予算をあと500円上げたら選択肢はどう変わるか」を確かめるコストが高すぎるため、たいていは最初に見つけた店で妥協します。幹事の負担が大きいだけでなく、**会そのものの質が下がります。**

## 2. 解決

ENCOPAは、この一連を1画面につなぎます。

| 幹事の作業 | ENCOPAでは |
|---|---|
| 店を探して見比べる | 条件を入れると実店舗を取得し、条件一致・予算・利便性の3点で採点して並べる |
| 良し悪しを判断する | AIが候補ごとの向き・不向きと、**予約前に店へ確認すべきこと**を添える |
| 候補をチャットに貼る | 招待リンクでグループを作り、予約内容をそのまま共有 |
| 出欠を集計する | 参加者が自分で回答。集計・所属・最終更新が一覧に並ぶ |
| アレルギーを聞いて回る | 本人が回答し、**本人と幹事だけ**が閲覧できる |
| 連絡文を書く | 予約内容と出欠から3種類の文面を自動生成し、編集してグループへ投稿 |
| カレンダーに入れる | 内容を確認してカレンダーファイルを書き出す |

**条件を変えれば、候補も理由も文面もその場で組み直されます。** やり直しのコストがゼロになることが、この製品の中心にある価値です。

## 3. 技術的な見どころ

このアプリの設計は、「**AIに何をさせないか**」を決めることで形が決まりました。OWASP Top 10 for LLM Applications 2026 / Agentic Applications 2026 を参照して監査した結果を反映しています（`docs/AUDIT-2026-09.md`）。

### 権限を最小にする（Excessive Agency対策）

**AIは外部操作を一切しません。** 予約もキャンセルも送信も行わず、候補の比較と文章の下書きまでで止まります。**エージェントが乗っ取られても、起きうる最悪のことは「おかしな比較コメントが表示される」ことです。** 勝手に予約が入ることはありません。

モデルが返した店舗IDは、こちらが渡した候補リストに含まれるものだけを採用します。存在しないIDを返しても無視されます。

### AIを使わないという判断（プロンプトインジェクション対策）

参加者へのお知らせ文は、**モデルを使わず**予約内容と出欠の集計だけから組み立てます。参加者が書いた表示名・所属・アレルギーの補足は文面の材料にしません。

混ぜると、**参加者の書いた文字列がそのままプロンプトになり、その出力がグループへ投稿される経路**ができるためです。材料が検証済みの値だけで足りるのに、その経路を作る理由がありません。副次的に、APIキーが無くてもモデルが落ちていても同じ文面が出ます。

### 止まらない、そして黙って嘘をつかない

店舗検索には、キャッシュ（30分）・再試行・サーキットブレーカー・縮退（最大24時間）・1日上限を実装しています。

- **再試行は直せる失敗だけ1回。** タイムアウト・5xxは再試行し、**認証拒否と429は再試行しません**。直らないうえ上限を消費し、利用者に伝えるべきエラーを遅らせるだけだからです
- **取得元が落ちても保存済みの結果で応答を続けます。** ただしその場合は必ず「保存済みの検索結果を表示しています」と取得時刻を画面に出します。**キャッシュを現在の情報として見せることが、閉店した店を予約させる経路になるためです**
- **1日上限は減速ではなく停止です。** 到達後は保存済みで返すか断り、追加の呼び出しはしません

### OrcaRouterへの依存を前提にしすぎない

ENCOPAではAgent OrchestrationとModel Routingを分けています。ENCOPAが「どの処理をどこまで実行するか」を決め、OrcaRouterには各LLMリクエストのルーティングを任せます。OrcaRouter側のフェイルオーバーは**best-effort**として扱い、ENCOPA自身もRetry・Timeout・Circuit Breaker・Graceful Degradationを持たせています。Routerがあることを理由に、アプリ側の障害対策を省略しません。

### コストを設計に入れる

店舗検索APIに渡している主な検索条件は**都道府県と人数**です。予算・優先条件・目的・個室希望・食事配慮は、取得後のENCOPA側の評価に使います。そのため**保存済みの店舗検索応答1件を、同じ地域・同じ人数の再評価に使い回せます。**

AI分析は、条件が単純なら**Coordinatorの1回**で済ませます。詳細分析が必要な場合は、3種類の専門担当から**会場比較担当 + 状況に応じたもう1担当の計2担当**を選び、最後に再統合します。基本はStandard 1回 / Detailed 4回で、自己検証が不備を見つけた場合だけ修正のために1回追加します（最大Standard 2回 / Detailed 5回）。

### 個人情報の扱い

アレルギー情報は**保存時にAES-256-GCMで暗号化**し、回答には本人の同意を必須にしています。参加者一覧に他人のアレルギーは表示されません。

出欠は**本人だけが変更できます**。代理回答の経路そのものを作っていないため、幹事でも他人の出欠は変えられません。未回答は参加に数えないので、黙っている人が人数を押し上げることもありません。

## 4. 完成度の裏付け

主張だけでなく、機械で検証しています。

| 検証 | 内容 |
|---|---|
| `pnpm test` | **37件**。一時DBと本番ビルドを起動し、権限分離・CSRF・再試行・ブレーカー・縮退・1日上限を実際に通します |
| `pnpm visual-check` | 320 / 390 / 834 / 1280 / 1536px **＋ダークモード**でブラウザ描画し、横スクロール・未ハイドレート・文字切れ・カーソル不正・コントロールの高さと背景の不揃いを検出 |
| `pnpm lint` / `typecheck` / `build` | 型・静的解析・本番ビルド |

`visual-check`は、**CSPを入れた際にヘッダもHTMLも正しいのにブラウザが画面を描けなかった事故**を受けて書いたものです。レスポンスの検査では通ってしまう種類の欠陥を、実際に描画して捕まえます。

## 5. できないこと

審査にあたって正直に書いておきます。

- **空席照会と予約操作は行いません。** 実際の予約は店舗ページまたは電話で行い、成立後に幹事が予約状況を登録します
- **ホットペッパーグルメWebサービスの商用利用条件は未確認です。** 公開運用の前に、キャッシュの可否と呼び出し上限の確認が必要です
- 認証はメールやSSOではなく、招待リンクとCookieによる軽量な方式です
- チャットの更新はリアルタイム通信ではなく15秒間隔のポーリングです

技術的な制約の全一覧は[既知の制約](#既知の制約)にまとめています。

## 6. 試す手順

デプロイ済みの画面は上記のデモURLで確認できます。手元で動かす場合は次の通りです。

```bash
pnpm install --frozen-lockfile
cp .env.example .env.local   # HOTPEPPER_API_KEY と ORCAROUTER_API_KEY を設定
pnpm dev
```

**APIキーが無くても、グループ作成・出欠・アレルギー回答・お知らせ文の作成は動作します**（店舗検索とAI分析のみ無効になります）。お知らせ文の生成にモデルを使っていないためです。なお開発環境で`ENCOPA_DATA_KEY`を設定しない場合、アレルギー情報は暗号化されずに保存されます。本番では必須です。

環境変数の一覧と本番設定は[ローカル起動](#ローカル起動)と[Vercelへデプロイ](#vercelへデプロイ)を参照してください。

## 機能一覧

- 47都道府県から場所を選び、予算・人数・個室などの条件で実在店舗を検索・比較
- OrcaRouterによる標準分析と、条件が難しい場合だけ行う専門担当の追加確認
