# ENCOPA（エンコパ）

**飲み会の幹事がやっている作業を、ひとつの流れにまとめるアプリです。**

| | |
|---|---|
| 動かすもの | 全国47都道府県の**実在する店舗**（ホットペッパーグルメWebサービス） |
| 使っているAI | OrcaRouter経由の多段エージェント（統括→専門担当→再統合） |
| 技術構成 | Next.js 16 / React 19 / TypeScript / Tailwind CSS v4 / Turso (libSQL) / Vercel |

---

## 1. 課題

忘年会の幹事を引き受けると、作業はこう散らばります。

> グルメサイトで店を探す → 条件に合うか一軒ずつ見比べる → チャットに候補を貼る → 出欠を集計表に書き写す → アレルギーの有無を個別に聞いて回る → 決まった内容をもう一度チャットに貼る → カレンダーに入れる

**店探し以外のすべてが手作業で、情報はサイト・チャット・表計算・カレンダーの4か所に散らばります。**

そして最大の問題は、**一度決めた条件を変えると最初からやり直しになる**ことです。「予算をあと500円上げたら選択肢はどう変わるか」を確かめるコストが高すぎるため、たいていは最初に見つけた店で妥協します。幹事の負担が大きいだけでなく、**会そのものの質が下がります。**

## 2. 解決

ENCOPAは、この一連を1画面につなぎます。

| 幹事の作業 | ENCOPAでは |
|---|---|
| 店を探して見比べる | 条件を入れると実店舗を取得し、条件一致・予算・利便性の3点で採点して並べる |
| 良し悪しを判断する | AIが候補ごとの向き・不向きと、**予約前に店へ確認すべきこと**を添える |
| 候補をチャットに貼る | 招待リンクでグループを作り、予約内容をそのまま共有 |
| 出欠を集計する | 参加者が自分で回答。集計・所属・最終更新が一覧に並ぶ |
| アレルギーを聞いて回る | 本人が回答し、**本人と幹事だけ**が閲覧できる |
| 連絡文を書く | 予約内容と出欠から3種類の文面を自動生成し、編集してグループへ投稿 |
| カレンダーに入れる | 内容を確認してカレンダーファイルを書き出す |

**条件を変えれば、候補も理由も文面もその場で組み直されます。** やり直しのコストがゼロになることが、この製品の中心にある価値です。

## 3. 技術的な見どころ

このアプリの設計は、「**AIに何をさせないか**」を決めることで形が決まりました。OWASP Top 10 for LLM Applications 2026 / Agentic Applications 2026 を参照して監査した結果を反映しています（`docs/AUDIT-2026-09.md`）。

### 権限を最小にする（Excessive Agency対策）

**AIは外部操作を一切しません。** 予約もキャンセルも送信も行わず、候補の比較と文章の下書きまでで止まります。**エージェントが乗っ取られても、起きうる最悪のことは「おかしな比較コメントが表示される」ことです。** 勝手に予約が入ることはありません。

モデルが返した店舗IDは、こちらが渡した候補リストに含まれるものだけを採用します。存在しないIDを返しても無視されます。

### AIを使わないという判断（プロンプトインジェクション対策）

参加者へのお知らせ文は、**モデルを使わず**予約内容と出欠の集計だけから組み立てます。参加者が書いた表示名・所属・アレルギーの補足は文面の材料にしません。

混ぜると、**参加者の書いた文字列がそのままプロンプトになり、その出力がグループへ投稿される経路**ができるためです。材料が検証済みの値だけで足りるのに、その経路を作る理由がありません。副次的に、APIキーが無くてもモデルが落ちていても同じ文面が出ます。

### 止まらない、そして黙って嘘をつかない

店舗検索には、キャッシュ（30分）・再試行・サーキットブレーカー・縮退（最大24時間）・1日上限を実装しています。

- **再試行は直せる失敗だけ1回。** タイムアウト・5xxは再試行し、**認証拒否と429は再試行しません**。直らないうえ上限を消費し、利用者に伝えるべきエラーを遅らせるだけだからです
- **取得元が落ちても保存済みの結果で応答を続けます。** ただしその場合は必ず「保存済みの検索結果を表示しています」と取得時刻を画面に出します。**キャッシュを現在の情報として見せることが、閉店した店を予約させる経路になるためです**
- **1日上限は減速ではなく停止です。** 到達後は保存済みで返すか断り、追加の呼び出しはしません

### OrcaRouterへの依存を前提にしすぎない

ENCOPAではAgent OrchestrationとModel Routingを分けています。ENCOPAが「どの処理をどこまで実行するか」を決め、OrcaRouterには各LLMリクエストのルーティングを任せます。OrcaRouter側のフェイルオーバーは**best-effort**として扱い、ENCOPA自身もRetry・Timeout・Circuit Breaker・Graceful Degradationを持たせています。Routerがあることを理由に、アプリ側の障害対策を省略しません。

### コストを設計に入れる

店舗検索APIに渡している主な検索条件は**都道府県と人数**です。予算・優先条件・目的・個室希望・食事配慮は、取得後のENCOPA側の評価に使います。そのため**保存済みの店舗検索応答1件を、同じ地域・同じ人数の再評価に使い回せます。**

AI分析は、条件が単純なら**Coordinatorの1回**で済ませます。詳細分析が必要な場合は、3種類の専門担当から**会場比較担当 + 状況に応じたもう1担当の計2担当**を選び、最後に再統合します。基本はStandard 1回 / Detailed 4回で、自己検証が不備を見つけた場合だけ修正のために1回追加します（最大Standard 2回 / Detailed 5回）。

### 個人情報の扱い

アレルギー情報は**保存時にAES-256-GCMで暗号化**し、回答には本人の同意を必須にしています。参加者一覧に他人のアレルギーは表示されません。

出欠は**本人だけが変更できます**。代理回答の経路そのものを作っていないため、幹事でも他人の出欠は変えられません。未回答は参加に数えないので、黙っている人が人数を押し上げることもありません。

## 5. できないこと

審査にあたって正直に書いておきます。

- **空席照会と予約操作は行いません。** 実際の予約は店舗ページまたは電話で行い、成立後に幹事が予約状況を登録します
- **ホットペッパーグルメWebサービスの商用利用条件は未確認です。** 公開運用の前に、キャッシュの可否と呼び出し上限の確認が必要です
- 認証はメールやSSOではなく、招待リンクとCookieによる軽量な方式です
- チャットの更新はリアルタイム通信ではなく15秒間隔のポーリングです

技術的な制約の全一覧は[既知の制約](#既知の制約)にまとめています。

## ローカル起動

Node.js 24とpnpm 11.19.0を使用します。

```bash
pnpm install --frozen-lockfile
cp .env.example .env.local
pnpm dev
```

ローカルでは`TURSO_DATABASE_URL`が空の場合、`data/encopa.db`を自動作成します。`.env.local`へ`ENCOPA_DATA_KEY`、[ホットペッパーグルメWebサービス](https://webservice.recruit.co.jp/doc/hotpepper/reference.html)の`HOTPEPPER_API_KEY`、[OrcaRouter](https://docs.orcarouter.ai/introduction)の`ORCAROUTER_API_KEY`を設定してください。暗号化キーは`openssl rand -hex 32`で生成できます。

## Vercelへデプロイ

1. このリポジトリをVercelへImportする
2. Tursoでデータベースを作成する
3. VercelのEnvironment Variablesへ以下を設定する
4. Deployする

| 変数 | 必須 | 用途 |
|---|---:|---|
| `TURSO_DATABASE_URL` | 本番必須 | 共有データベースURL |
| `TURSO_AUTH_TOKEN` | 本番必須 | Tursoのサーバー専用トークン |
| `ENCOPA_DATA_KEY` | 本番必須 | 予約内容とアレルギー情報をAES-256-GCMで暗号化する32バイト鍵 |
| `APP_ORIGIN` | 本番必須 | `https://example.com`形式の公開Origin |
| `HOTPEPPER_API_KEY` | 本番必須 | 実店舗検索。ブラウザへ公開しないサーバー専用キー |
| `ORCAROUTER_API_KEY` | 本番必須 | 候補分析。ブラウザへ公開しない`sk-orca-*`キー |
| `ORCAROUTER_BASE_URL` | 任意 | 既定値はHosted版の`https://api.orcarouter.ai/v1` |
| `ORCAROUTER_ALLOWED_HOSTS` | 任意 | 信頼するセルフホスト接続先を追加する場合のみ指定 |
| `ORCAROUTER_MODEL` | 任意 | 既定値はOrcaRouterのAuto Routerを使う`orcarouter/auto` |
| `ENCOPA_AGENT_DAILY_LIMIT` | 任意 | 1日あたりの分析ワークフロー上限。既定100 |
| `ENCOPA_AGENT_DETAILED_DAILY_LIMIT` | 任意 | 1日あたりの詳細分析上限。既定30。上限後も標準分析は継続 |
| `ENCOPA_VENUE_DAILY_LIMIT` | 任意 | 1日あたりの店舗検索API呼び出し上限。既定1000。上限後は保存済みの応答で返すか停止します |
| `ENCOPA_VENUE_IP_HOURLY_LIMIT` | 任意 | 1IPあたりの店舗検索上限。既定30回/時 |
| `ENCOPA_VENUE_BREAKER_COOLDOWN_MS` | 任意 | 連続失敗後に呼び出しを止める時間。既定60000 |

秘密値に`NEXT_PUBLIC_`を付けないでください。Vercelのローカルファイルシステムは永続化されないため、本番で`file:`データベースは使用できません。

## レンダリング方式とCSP

`middleware.ts`がリクエストごとにnonceを発行し、`script-src`は`'nonce-...' 'strict-dynamic'`で構成します（`'unsafe-inline'`は含みません。併記している`'unsafe-inline'`と`https:`は`strict-dynamic`非対応ブラウザ向けの後方互換で、対応ブラウザでは無視されます）。

厳格なCSPはレスポンスごとに異なるnonceを必要とし、**プリレンダリング済みのページはそれを持てません**（ビルド時のHTMLにはnonce属性が無く、全スクリプトがブロックされます）。そのため`app/layout.tsx`で`export const dynamic = 'force-dynamic'`を指定しています。`pnpm build`の出力で`/`が`○ (Static)`になっていたらこの指定が外れています。`tests/agent.test.mjs`の「every script carries the nonce from this response」がこの退行を検出します。

ホットペッパーの店舗画像（`imgfp.hotp.jp`）は`img-src`で明示的に許可しています。

## 候補分析のコスト管理

標準計画は通常1回、詳細分析は通常4回の経路呼び出しを使います。自己検証で不備を検出した場合だけ、修正のために1回追加されるため、最大はStandard 2回 / Detailed 5回です。3段の歯止めがあります。

| 仕組み | 既定 | 挙動 |
|---|---|---|
| 計画キャッシュ（メモリ＋`encopa_agent_cache`） | TTL 30分 | 同一条件・同一候補の再実行で呼び出し0回 |
| クライアント単位 `ENCOPA_AGENT_IP_HOURLY_LIMIT` | 10件/時 | 1人が全体予算を使い切れない |
| サイト全体 `ENCOPA_AGENT_DAILY_LIMIT` / `ENCOPA_AGENT_DETAILED_DAILY_LIMIT` | 100 / 30件/日 | 詳細分析の枠を使い切ると標準計画へ縮退 |

一時的な失敗（429・5xx・タイムアウト）は1回だけ再試行し、リクエスト形式を拒否された場合（4xx）は最小構成で1回だけ再試行します。連続3回失敗すると`ENCOPA_AGENT_BREAKER_COOLDOWN_MS`の間、呼び出し自体を停止します。

## データとセキュリティ

- 認証情報は32バイトのランダム値をCookieへ保存し、DBにはSHA-256ハッシュだけを保持します。
- 予約内容とアレルギー情報はAES-256-GCMで暗号化して保存します。既存の平文レコードは読み取り互換を維持し、更新時から暗号化されます。
- CookieはHttpOnly、SameSite Strict、本番ではSecureです。
- POSTは同一Origin、JSON、16KiB以下に制限します。
- グループ作成は送信元ごとに1時間10回、全体で1時間300回へ制限します。
- 予約番号は既定で幹事だけに返し、幹事が明示的に許可した場合だけ参加者と予約共有メッセージに表示します。
- グループは90日、参加セッションは30日、招待リンクは7日で期限切れになります。
- チャットは最新100件を表示します。
- 店舗検索は送信元ごとに1時間30回へ制限し、外部APIは8秒でタイムアウトします。
- 店舗検索結果はTurso / libSQLの`encopa_venue_cache`へ保存します。通常利用のFresh TTLは30分で、店舗検索元が利用できない場合に限り最大24時間までの保存済み結果を縮退表示し、取得時刻を画面に明示します。
- 候補分析へ送るのは検索条件と公開店舗情報だけです。氏名、連絡先、アレルギー品目は送信しません。
- OrcaRouterの接続先は`api.orcarouter.ai`と明示的に許可したホストだけに制限し、APIキーの誤送信を防ぎます。
- 候補分析は送信元ごとに1時間10回、全体では設定した日次上限に制限します。通常はOrcaRouterを1回、詳細分析は4回を基本とし、自己検証で不備が見つかった場合だけ修正のため1回追加します（最大Standard 2回 / Detailed 5回）。詳細分析には別の日次上限を設定できます。
- グループ削除は復元できません。期限切れデータは`pnpm db:cleanup`で削除できます。
- 本格運用では、管理者が定期クリーンアップ、バックアップ、監視、障害対応を設定してください。

## 既知の制約

- メールアドレス認証やSSOではなく、招待リンクとブラウザCookieによる軽量な参加方式です。
